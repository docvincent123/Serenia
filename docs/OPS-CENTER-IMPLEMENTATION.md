# SOLVIA Ops Center — Linux та оперативна передача зміни

Цей етап доповнює `feature/rehab-center-readiness`. Не є підтвердженням встановлення в центрі.

## Топологія

- Окремий Ubuntu 24.04 LTS x86_64, PostgreSQL 16 по Unix socket (TCP БД вимкнений), `solvia.service` на HTTPS/8443, `solvia-http.service` тільки localhost/8765. Сервіс запускає systemd незалежно від графічного клієнта.
- Windows/Linux/Android під'єднуються через TLS до стабільного DNS або LAN-адреси; файл `.solvia` містить адресу й server_id, не паролі. Віддалений доступ тільки через VPN/TLS, не відкривати PostgreSQL в інтернет.
- Звичайний адміністратор входить у Server Console зі свого ПК. Root-команди `backup`, `restore`, `restart`, `update`, SSH/VPS залишаються окремими Linux-операціями. Web API не виконує довільних shell-команд.

## Реалізовано в цьому PR

1. GET `/api/admin/system` (тільки admin) повертає `host_resources` із доступним диском, загальною і фізично вільною RAM, 1-хв Linux load та uptime; для Windows/недоступних метрик — явний unavailable. Дані не містять секретів/процесних параметрів.
2. `api_timing`: успішні запити, максимальне очікування на глобальному mutex і найбільший час обробки від запуску **конкретного API-процесу**. Це не p95 і не загальносистемний моніторинг двох API-процесів.
3. Server Console показує стан Linux, PostgreSQL, локальних/віддалених backup events і shift jobs. Попередження: зайнято >=90% диска, немає свіжої перевіреної локальної копії в межах 36 год, немає підтвердження VPS, останній offsite failed, невдале завдання зміни.
4. `shift_handover`: окрема таблиця лише організаційних справ (до 300 символів), пріоритет normal/important/urgent, open/resolved, автор, дата, виконавець, аудиторський слід. Завдання залишаються між змінами; повтор із тим самим client_key не створює дубля навіть між HTTPS і loopback API-процесами.
5. Ролі: admin/reception можуть читати й вести передачу; реєстратура може змінювати тільки з наданим активним доступом; psychologist/director не мають API-доступу до цих даних. Приватні нотатки консультацій не записуються в цей журнал.
6. На ПК з'являється окремий розділ «Передача зміни» в каталозі функцій. Робочий процес: створити → побачити у списку → позначити виконаним. Є фільтр завершених.

## Приймання на Linux

Після створення backup і синхронного оновлення сервера/клієнтів:

```bash
sudo solvia-admin status
sudo solvia-admin health
sudo solvia-admin doctor
sudo systemctl list-timers 'solvia-*'
sudo solvia-admin backups
sudo solvia-continuity remote-check
```

`remote-check` потребує реально налаштованого зашифрованого сховища. Не змінюйте продуктивну БД без перевіреного плану повернення.

Тестові сценарії на синтетичних пацієнтах:
- Адмін/реєстратура створюють завдання, перезапускають клієнт та передають його наступній зміні.
- Повторення POST після втрати відповіді не створює дубль; спроба з тим самим ключем та іншим текстом → HTTP 409.
- Психолог/керівник отримують HTTP 403 для handover та admin/system; працівник без активного дозволу не може записати завдання.
- Linux-діагностика не показує вигадані значення, коли не має дозволу або ресурсу.
- На двох ПК паралельно відкривають ту саму зміну; створення/виконання не перезаписує чужі завдання.
- Реальна перевірка 40 користувачів, втрата живлення та Wi-Fi, відкриті Android-чернетки, оновлення сервер + клієнт, резервування на VPS, відновлення на чистій машині.

## Наступні роботи — поки НЕ реалізовані

1. Прибрати загальний mutex лише після переходу з одного DB-з'єднання на керований пул, окремих транзакцій, перевірки блокувань та тестів конкурентного бронювання, консультацій, передачі зміни, повторних запитів. Вхідні навантажувальні дані з реального Linux і клієнтів.
2. MFA/Passkeys для адміна; обмеження прав привілейованого доступу і security review; перевірка політик доступу до медданих.
3. WAL archive + PITR і незалежне розгортання відновленої копії. Мінімальний retention для локальних копій — окреме перевірене правило з dry-run, достатнім строком, підтвердженням offsite та забороною випадково видалити останню коректну копію.
4. Зовнішній Linux-health агент, який бачить відсутність відповіді сервера (веб-панель не може повідомити, коли сам сервер недоступний). Канал аварійних сповіщень лише після підтвердження одержувачів, без ПІБ і медичних даних.
5. Повноцінне звернення з номером, датами, SLA, призначенням відповідального, ескалаціями і статусами; версійні міграції даних та правила згідно зі сценаріями реабцентру.
6. Контрольований restore/failover із виключенням подвійного запису в стару та нову БД, фізична перевірка Android і TV та контрольоване розгортання.

Рекомендація: не об'єднувати всі ці ризикові зміни в один PR та не встановлювати неперевірений серверний код на реальній базі пацієнтів.
