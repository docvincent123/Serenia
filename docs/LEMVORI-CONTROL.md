# Lemvori Control — видавець і центри

Lemvori Control — окрема нативна програма для власника LemvoriLab. Вона створює ключ видавця, веде локальний реєстр центрів, підписує ліцензії та правила роботи. У центр передаються **публічний ключ** і файл `.lemvori-license`. Приватний ключ залишається у власника в PEM PKCS#8 із шифруванням та паролем. Реальних ключів у репозиторії або збірках немає.

Програма не отримує пацієнтів, консультацій чи резервних копій. Наявний `operator-hub` продовжує обслуговувати центральний реєстр і технічні heartbeat; медичні дані не додаються до цього каналу. У Control можна імпортувати запит центру, створений у Lemvori Care Admin, і видати файл для активації без інтернету. Це не реалізація онлайн-білінгу або сервера дистанційного відкликання ключів.

## Як видати ліцензію

1. У Control натисніть «Новий ключ видавця», задайте й підтвердьте пароль, виберіть нову папку. Збережіть захищену резервну копію приватного ключа та пароль окремо.
2. На Linux-сервері центру встановіть лише публічний ключ, наприклад `/etc/solvia/license-public.pem`, і налаштуйте `SOLVIA_LICENSE_PUBLIC_KEY` на цей шлях для SolviaServer. Для комерційного розгортання встановіть `SOLVIA_LICENSE_REQUIRED=1`.
3. У **Lemvori Care Admin → Ліцензія центру → Файл запиту для видавця** збережіть JSON. У ньому є лише назва, ID сервера та перелік модулів.
4. Відкрийте запит у Control, виберіть модулі та ліміти. Дата включає весь зазначений день за часом Києва. Порожній строк дії означає безстрокову ліцензію; підтримка має окрему дату та не скасовує безстрокове користування.
5. За потреби на вкладці «Правила роботи» позначте їх застосування: години, дні `1234567`, крок запису, тривалість прийому та час сеансу входу. Ці поля входять у цифровий підпис і застосовуються транзакційно при активації.
6. Натисніть «Видати файл ліцензії», введіть пароль приватного ключа. Передайте створений файл у центр.
7. Адміністратор центру імпортує файл у **Ліцензія центру**. Сервер перевіряє Ed25519, власний ID, строк, модулі, версії, залежності та ліміти. Приватний ключ центру не потрібен.

Формат зовнішнього конверта сумісний із наявним `quremed.solvia.license`. Нові ключі мають payload `version: 2`. Старі ліцензії продовжують перевірятися. Без налаштованого публічного ключа старі розгортання залишаються в режимі `unmanaged`; прапорець `SOLVIA_LICENSE_REQUIRED=1` прибирає цей виняток у керованому центрі.

Підпис перевіряється при кожній операції, яка змінює дані. Завершення ліцензії не видаляє записи та не блокує читання чи експорт. Вимкнення модуля блокує нові операції в ньому; доступ до вже збережених даних додатково визначає роль працівника. Ліміти перевіряються сервером при створенні/активації працівника та вході з нового пристрою.

## Модульність

Маніфест `publisher/modules.json` містить ID, назву, версію, базовість і залежності. Серверна копія — `src/server/module_catalog.h`; тест перевіряє їхню відповідність. Картки, документи та згоди — базові. Інші модулі вмикаються в межах підписаної ліцензії й налаштувань центру. Професійна посада не розширює серверну роль; індивідуальні заборони працівника зберігаються поверх ліцензії.

Новий модуль додається разом із реалізацією API/клієнта, маніфестом, залежностями, міграціями й тестами, після чого випускається сумісне оновлення Control і сервера. Завантаження довільного коду або SQL із ліцензійного файла не дозволене. Галочка не створює відсутній клінічний процес.

## Згоди та реєстрація

У керованому центрі з ліцензією v2 перевірку підписаних згод вимкнути не можна. У режимі сумісності `unmanaged` є налаштування для поетапного переходу; нова інсталяція починає з увімкненою перевіркою.

Адміністратор затверджує тексти у **Правила згод**. Готового юридичного тексту програма не підставляє: порожній обов’язковий шаблон зупиняє друк і завершення реєстрації. Зміна тексту створює нову версію.

Реєстратура заповнює дані, зберігає PDF бланків, відкриває його для друку, отримує власноручні підписи та завантажує PNG/JPEG оригіналів. Працівник указує підписанта й підтверджує перевірку підпису на папері. Система перевіряє наявність скану, версію, текст, ПІБ/дату народження та посилання на реєстрацію; вона не розпізнає справжність почерку і не створює КЕП.

Картка, курс і документи зберігаються в одній транзакції. За помилки скану або застарілої версії частково зареєстрованої картки не залишається. Якщо ПІБ чи дата народження змінені після друку, клієнт вимагає нових бланків. У картці видно комплектність згод; зміна цих полів після збереження робить попередній комплект неактуальним.

Історія консультацій та повний PDF доступні адміністратору; реєстратура друкує реєстраційну картку без приватних консультацій. Керівник працює з виписками та аналітикою відповідно до ролі.

## Шифрування даних

Ліцензійний підпис не шифрує медичні картки. Для захисту всієї PostgreSQL, індексів, журналів і файлів використовується шифроване серверне сховище LUKS2. Підготовка нового тому — `deployment/create-encrypted-storage.sh`; перевірка ланцюжка пристрою — `tools/check-encrypted-storage.py`.

Скрипт створює тільки новий файловий том, не форматує наявний диск і не переносить робочу БД. Пароль запитується cryptsetup і не зберігається програмою. Розміщення PostgreSQL, документів, локальних копій, керування розблокуванням при завантаженні та перевірене відновлення виконуються під час розгортання на сервері центру. До такого перенесення називати робочу базу зашифрованою не можна.

Наявний `solvia-continuity` з restic залишається механізмом перевірених зашифрованих зовнішніх копій; локальні `.dump` потрібно тримати всередині захищеного тому. Android уже використовує AES-256-GCM та Android Keystore для приватного офлайн-журналу. Нативний ПК-клієнт тримає сеанс і відкриту картку в оперативній пам’яті; експортований користувачем PDF потребує захищеного робочого сховища.

## Складання Control

```bash
python3 -m pip install -r publisher/requirements.txt
python3 publisher/main.py
```

Workflow **Lemvori Control native publisher** створює окремі виконувані файли Windows/Linux. Ключі у виконувані файли не вбудовуються. Qt-клієнти збираються workflow **Lemvori Care native desktop**. Сервер оновлюється окремо, після перевіреної резервної копії БД.
