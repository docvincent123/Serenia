# SOLVIA 2.2 — Linux-сервер і Windows-клієнти

Пакет підтримує **Ubuntu 24.04 LTS x86_64 та elementary OS 8 на базі Ubuntu 24.04**. Для іншої версії Linux потрібна окрема перевірка сумісності. Docker, Node.js та компілятор на сервері не потрібні. Інтернет потрібен під час встановлення системних пакетів; щоденна робота відбувається в LAN.

## 1. Встановлення Linux-сервера

У GitHub Actions відкрийте успішну збірку **SOLVIA • Desktop installer and PostgreSQL tests**, завантажте artifact **SOLVIA-2.2.0-Linux-x64-installer**, розпакуйте ZIP, потім:

```bash
tar -xzf SOLVIA-2.2.0-Linux-x64.tar.gz
cd SOLVIA-Linux
sudo bash install.sh
```

Майстер запитає логін, ПІБ, пароль першого адміністратора й приватну IPv4-адресу сервера. Закріпіть цю адресу через DHCP reservation на роутері або статичні налаштування Linux. Приклад: `192.168.1.105`. Виберіть правильний часовий пояс сервера (`timedatectl`): від нього залежить робоча зміна й розклад резервних копій.

Інсталятор перевірить SHA-256 файлів, установлює PostgreSQL 16, створює **окремий кластер `16/solvia`** і базу `solvia`, служби та сертифікати. Також він встановлює **SOLVIA Admin** у меню програм Linux і додає локальний QureMed CA до системного сховища довіри. Інші кластери PostgreSQL і RehaFlow не переналаштовуються. SOLVIA використовує Unix socket PostgreSQL з ідентифікацією системного користувача `solvia`; пароль БД не потрібний. Порт кластера 55432 використовується для імені сокета, TCP вимкнений.

Вихідна адреса: **`https://192.168.1.105:8443`**. Linux використовує власний HTTPS-слухач SOLVIA; Caddy й Windows Task Scheduler йому не потрібні. Після встановлення адміністратор запускає **SOLVIA Admin** з меню програм. Launcher читає публічну копію поточної адреси з `/usr/local/share/solvia/address`, перевіряє HTTPS і відкриває SOLVIA як окреме app-вікно Chrome/Chromium/Edge/Brave або у Firefox/браузері за замовчуванням. При помилці `install.sh` повертає ненульовий код та не видаляє базу.

Якщо UFW уже активний, дозвольте порт лише для фактичної підмережі центру, наприклад:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 8443 proto tcp
```

Інсталятор не змінює загальну політику firewall, не відкриває PostgreSQL і не налаштовує port forwarding на роутері.

## 2. Windows-ПК

Завантажте artifact **SOLVIA-2.2.0-Setup-EXE** тієї самої збірки. У майстрі виберіть **«Робоче місце — підключення до Linux-сервера»** (тип за замовчуванням) і введіть адресу HTTPS. На робочому ПК PostgreSQL і сервер не встановлюються.

1. На Linux скопіюйте **лише** `/etc/solvia/ca/QureMed-Local-CA.crt` на довірений носій. Приватний `ca.key` ніколи не переноситься на клієнт.
2. На Windows у меню Пуск відкрийте **«Довірити сертифікат сервера SOLVIA»**.
3. Виберіть `.crt`, звірте SHA-256 з відбитком, показаним Linux-інсталятором, і підтвердьте. Довіра додається для поточного Windows-користувача. Кожен Windows-профіль робить це окремо.
4. Відкрийте SOLVIA → «Налаштувати адресу сервера» → «Перевірити та зберегти адресу» → увійдіть.

Адреса з майстра зберігається в `client-server.txt` поруч із `Solvia.exe`; обрана користувачем адреса має пріоритет і зберігається у профілі WebView2. Пароль у цьому файлі не зберігається. На Windows потрібен Microsoft Edge WebView2 Runtime. За його відсутності встановіть Evergreen Runtime з офіційного сайту Microsoft.

Для Android імпортуйте той самий CA через налаштування безпеки Android, потім введіть адресу HTTPS. Браузер на Linux також може відкрити цю адресу після встановлення довіри до CA. Не вимикайте перевірку TLS.

## 3. Робота центру

Перший адміністратор створює працівників із ролями «Реєстратура», «Психолог», «Керівник». Адміністратор відкриває робочу зміну. Далі: реєстратор створює пацієнта та запис → психолог відкриває свою картку, додає консультацію, нотатку, цілі, план і домашнє завдання → керівник бачить агреговану статистику. Доступи перевіряє сервер. Реєстратура й керівник не отримують приватних нотаток.

Наявні модулі: індивідуальні й групові записи, перенесення/скасування, кабінети, сімейні зв’язки, анкета самоспостереження з посиланням для пацієнта й історією результатів, виписки, звіти за зміну, керування командою, сесіями та аудит. Поточна анкета — авторська анкета самоспостереження, не діагностична шкала.

Оплати/пакети, SMS/Telegram/push, повний кабінет пацієнта та інтеграція RehaFlow залишаються майбутніми модулями: наявність запису в `module_settings` не означає готової інтеграції.

## 3.1. Модулі SOLVIA 2.2

Для адміністратора та керівника доступний окремий контроль завантаження психологів. Показуються активні пацієнти, консультації за сьогодні й поточний тиждень, відміни, середня тривалість і розрахунок вільних годин на основі робочого вікна календаря 08:00–20:00.

Супервізії не прив'язуються до конкретного patient ID: психолог вносить лише деідентифікований опис випадку, а керівник/адміністратор планує зустріч та фіксує рекомендації.

Картка пацієнта містить джерело звернення, подальші направлення, історію курсів і підписані документи. Підпис виконується пальцем або стилусом на планшеті. Збережений документ можна відкрити в картці та надрукувати/зберегти як PDF.

Архів працює через курси: завершення активного курсу переводить картку в архів. Повторне звернення створює наступний курс у тій самій картці та повертає її до активної роботи; попередні консультації, документи й направлення не видаляються.

Керівницька аналітика агрегує тільки операційні показники та не повертає приватні тексти психологічних консультацій.

## 4. Обслуговування на Linux

```bash
sudo solvia-admin health
sudo solvia-admin status
sudo solvia-admin logs
sudo solvia-admin restart
sudo solvia-admin version
sudo solvia-admin check-update
sudo solvia-admin update
sudo solvia-admin backup
sudo solvia-admin backups
sudo solvia-admin db-status
sudo solvia-admin doctor
sudo solvia-admin restore /path/backup.dump
```

Служба `solvia` запускається після завантаження Linux і перезапускається після аварійного завершення. Журнал: `journalctl -u solvia`. Сертифікат перевіряється щодня й автоматично перевидається, коли залишилося менше 30 днів. CA зберігається між оновленнями; його термін — 10 років.

Резервні копії створюються щодня о 02:00 (за часом сервера); пропущена копія виконається після ввімкнення. Успішні backup/restore записуються в `backup_events`, а Linux Admin показує адміністратору стан БД, її розмір, кількість пацієнтів/консультацій/виписок та останні події резервування. Файли `/var/backups/solvia/*.dump` доступні тільки root. Вони **не видаляються автоматично**: контролюйте вільне місце та регулярно переносіть перевірені копії на інший носій. Копія на тому самому диску не захищає від його відмови. Окремо зберігайте захищену копію `/etc/solvia`, включно з CA-ключем, для відновлення довіри клієнтів.

Відновлення просить ввести `ВІДНОВИТИ`, зупиняє API, робить копію поточного стану та відновлює в одній транзакції. Якщо відновлення не вдалося, служба залишається зупиненою для перевірки; журнал показує причину. На Windows-клієнті розділ обслуговування Linux показує відповідні команди замість запуску локальних Windows-скриптів.

## 5. Оновлення, зміна адреси, перенесення

Після першого встановлення пакета з updater більше не потрібно вручну завантажувати кожний Linux tar.gz. Перевірка нової версії:

```bash
sudo solvia-admin check-update
```

Оновлення:

```bash
sudo solvia-admin update
```

Updater читає останній GitHub Release SOLVIA, завантажує Linux-пакет і окремий SHA-256, перевіряє контрольну суму, створює backup, запускає штатний installer поверх існуючої системи та після оновлення виконує HTTPS health-check. Облікові записи, PostgreSQL-база, CA та адреса сервера зберігаються.

У меню програм для **SOLVIA Admin** також є дія **«Оновити SOLVIA»**. Вона відкриває термінал і запускає той самий updater з `sudo`.

Для підготовки випуску використовується GitHub Actions workflow **SOLVIA Product Release**. Версія має збігатися з `project(Solvia VERSION ...)` у CMake. Після перевірок Windows, Linux і Android workflow створює чернетку GitHub Release з установниками та `.sha256`; публікація виконується окремо. Для Android потрібен постійний ключ підпису. Докладніше: [RELEASES.md](RELEASES.md).

Ручне повторне `sudo bash install.sh` залишається запасним способом оновлення. Перед міграціями інсталятор створює `pre-update-*.dump`. Попередній виконуваний файл і UI залишаються під `/opt/solvia` з суфіксом `.previous`; автоматичного відкочування змін схеми немає.

При зміні LAN-адреси повторіть установлення з новою адресою:

```bash
sudo SOLVIA_SERVER_IP=192.168.1.106 bash install.sh
```

CA зберігається, сертифікат сервера перевидається. На ПК змініть адресу на екрані входу. Не видаляйте `/etc/solvia/ca` для виправлення мережевої помилки.

**Існуюча база Windows автоматично не переноситься.** Windows-інсталятор використовує PostgreSQL 17, цей Linux-пакет — PostgreSQL 16. Зниження версії через restore не гарантується. Якщо в Windows уже є потрібні дані, спершу збережіть backup і виконайте окремо перевірене перенесення на сумісну версію PostgreSQL; не замінюйте робочу базу порожньою Linux-базою.

Для зупинення без видалення даних: `sudo systemctl disable --now solvia solvia-backup.timer solvia-certificate.timer`. Видалення PostgreSQL-кластера не входить до інсталятора.


## 6. Linux Admin

Після успішного встановлення в меню Ubuntu/elementary OS з'являється **SOLVIA Admin**. Команда ручного запуску:

```bash
solvia-admin-app
```

Linux Admin використовує той самий захищений API та RBAC, що й майбутні Windows/Android/iPhone клієнти. Адміністратор має доступ до пацієнтів, реєстрації, сімей, календаря, консультацій, виписок, персоналу, ролей, кабінетів, активних сесій, завершення сесій, статистики, налаштувань, audit log та admin-only діагностики PostgreSQL.

Небезпечні root-операції навмисно не виконуються через віддалений HTTP API. Повне відновлення БД, перезапуск сервісу та ручний backup виконуються локально через `sudo solvia-admin ...`. Це зменшує ризик знищення даних у разі викрадення адмінської web-сесії.

Для видалення програми без видалення даних використовуйте `sudo bash uninstall.sh`. Повне видалення локальної БД доступне тільки через `sudo bash uninstall.sh --purge-data` із додатковим ручним підтвердженням.


## Unified releases

The former Linux-only release workflow now runs the verified Linux, Windows and Android pipelines and creates a draft product release. It no longer accepts a separate version input: CMake and the source versions define the release. Permanent Android signing is required. Read `docs/RELEASES.md` for the exact release and customer update procedure.
