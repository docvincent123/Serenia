# Робочі сценарії SOLVIA 3.1: надійність у мережі центру

Основа: `ux/solvia-helsi-like-desktop`, commit `f4c588a`. Вона вже містить останні функції гілки `feature/solvia-patient-rehabilitation`. Ця зміна зберігає наявний білий інтерфейс і всі розділи.

## Що виправлено

- Запис на прийом шукає пацієнтів на сервері сторінками по 8 записів. Він більше не завантажує весь реєстр. Вибрані учасники залишаються у формі при пошуку й переході між сторінками; новий пацієнт одразу підставляється за своїм ID.
- Після втрати відповіді повторне збереження незміненої відкритої форми повертає номер уже створеного прийому. Серверна квитанція належить автору запиту; змінений текст із тим самим ключем повертає конфлікт. Повтор не створює нових подій, записів аудиту або прийомів. Після зміни полів форма створює новий ключ. Це не черга офлайн-бронювання після закриття браузера.
- При перенесенні власний прийом виключається з підказок зайнятості. Зайнятість інших прийомів продовжує перевірятися; остаточна перевірка й запис залишаються в одній транзакції.
- Якщо завантаження іншої дати календаря не вдалося, записи попередньої дати й їхні дії приховуються. Запізніла відповідь не замінює поточну дату.
- Спільний транспорт відправляє JSON `{}` для команд без тіла, зокрема виходу. Сервер тепер отримує коректну команду й анулює сесію. Перервана відповідь, HTML замість JSON, порожня відповідь і перенаправлення дають явну помилку.
- CMake відстежує зміни SQL-схеми й автоматично оновлює вбудовану схему під час наступної збірки.

Оновлювати сервер та frontend потрібно разом. Нова таблиця `appointment_requests` створюється без видалення наявних даних при запуску сервера.

## Перевірено в хмарному середовищі

- Production-збірка React/Vite та C++20-сервера.
- 22 інтеграційні тести на справжньому HTTP-сервері й PostgreSQL 17, включно з ролями, реабілітаційними цілями, документами, чернетками, повтореннями запитів, конкуренцією 40 працівників, змінами й відновленням.
- 11 браузерних наборів проти production-збірки із синтетичними API-відповідями: чотири ролі, запис/перенесення, календарні помилки, документи/друк, черги, відновлення пристроїв, повідомлення, TV, офлайн-вхід та оновлення ПК.
- Перевірки JavaScript-моделей, ліцензій і continuity.
- Окремий HTTPS-запуск із `--host 0.0.0.0`: завантаження production UI, перевірка сертифіката довіреним тестовим CA, вхід і справжнє анулювання сесії через спільний клієнтський транспорт. Перевірка TLS не вимикалася.

## Перед установленням у центрі

Це код для перевірки й випуску, а не вже розгорнуте оновлення. Windows WebView2/інсталятор і фізичні Android/TV/принтер у цій машині не запускалися.

Використайте інструкції [підключення центру](CENTER-ACCESS.md) та [Linux](LINUX.md): постійне DNS-ім'я, довірений CA на кожному ПК/Android і актуальний файл `.solvia`. Не вимикайте TLS і не відкривайте порт PostgreSQL клієнтам.

На двох робочих місцях центру перевірте реєстрацію → запис → прибуття → консультацію → огляд керівника; одночасний запис в один слот; коротке вимкнення Wi-Fi та повтор збереження; вихід і повторний вхід. Фізичну LAN центру хмарне тестування не перевіряє. Успішні автоматичні тести не є гарантією відсутності всіх помилок.
