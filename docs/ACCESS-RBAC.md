# Lemvori Care: посади, ролі та розділення доступу

## Принцип

**Роль доступу** (`admin`, `reception`, `psychologist`, `director`) визначає базовий серверний набір дозволених операцій. **Посада** (`job_title`) та **напрямок** (`primary_service_code`) — окремі довідкові поля; жодне з них не підвищує базових прав. Це важливо для лікарів, медсестер, фізичних терапевтів, ерготерапевтів, логопедів, соціальних працівників та арттерапевтів: призначення посади не відкриває приватні записи психолога.

## Рівні захисту

1. **Перевірка ролі на сервері**: існуючі `allow(...)` залишаються чинними.
2. **Обмеження конкретного працівника**: таблиця `user_module_blocks` містить лише заборони, не додаткові дозволи.
3. **Перевірка кожного API-запиту**: `moduleForApi()` відносить ключові запити до модулів; при забороні сервер повертає HTTP 403. Доступ до детальної картки пацієнта також закривається, якщо заборонено клінічні записи, документи чи реабілітацію, оскільки відповідь старого API містить вкладені приватні дані.
4. **Нативний Qt-клієнт**: `/api/my-module-permissions` синхронізується під час оновлення; недоступні розділи приховані. Це UX, не заміна серверної авторизації.
5. **Аудит**: `update_permissions` записується в журнал із виконавцем і цільовим користувачем.

Модулі, для яких доступне індивідуальне обмеження:

| Код | Ділянки |
| --- | --- |
| `patients` | Пацієнти, реєстр, сім’ї |
| `appointments` | Запис, час, прийоми, календар, лист очікування |
| `clinical` | Консультації, оцінки, клінічні нотатки |
| `rehabilitation` | Реабілітаційні записи |
| `documents` | Виписки, документи, шаблони |
| `reports` | Аналітика та звіти |
| `messages` | Повідомлення працівників |
| `roster` | Склад спеціалістів на зміні |

Це додатковий захисний рівень для перерахованих API-маршрутів, **не універсальна система налаштовуваних дозволів для кожної функції сервера**. Доступ до інших функцій, зокрема системного адміністрування, як і раніше обмежує чинна роль.

## Як користуватися

У **Lemvori Care Admin → Працівники** встановіть роль доступу, посаду, професійний напрямок. Для індивідуальних обмежень відкрийте **Права за модулями**, знайдіть працівника й натисніть **Налаштувати права**. Вимкнений перемикач означає заборону модуля. Адміністраторські акаунти не змінюються цим інтерфейсом. Операція не завершує чужих сесій: при наступному оновленні клієнт отримає нові обмеження, а сервер застосовує їх одразу.

## Порядок впровадження

1. Зробіть перевірену резервну копію PostgreSQL перед зміною схеми.
2. Оновіть **SolviaServer**: ідемпотентні SQL-зміни додають `users.job_title` та `user_module_blocks`; наявні ролі й облікові записи зберігаються.
3. Перевірте тестові акаунти ролей: адміністратор, реєстратор, психолог, керівник. Переконайтеся, що обмежена роль отримує 403 для закритого API й не може повернути собі доступ.
4. Встановіть оновлений Qt-клієнт на робочі місця, перевірте TLS, запис, документи, зміни, запуск і завершення сеансів.
5. Лише після тестування — ввімкніть обмеження для реальних працівників.

**До окремого етапу:** серверні процеси для нових незалежних клінічних ролей (лікар, медсестра, фізичний терапевт, логопед тощо), доступ до їхніх призначень, пацієнтських кейсів і спеціалізованої документації. Присвоєння професійної посади сьогодні не означає надання цих прав.
