# SOLVIA: нічні копії, зміни, оновлення і VPS

## Що встановлюється

- `solvia-nightly.timer`: щодня **00:00 Europe/Kyiv**, з урахуванням літнього часу. Пропущений запуск виконується після ввімкнення серверного ПК.
- `solvia-shift-backup.timer`: кожні 60 секунд перевіряє стійку чергу `shift_backup_jobs`. Закриття зміни й постановка копії в чергу — одна транзакція. Робота не блокується довгим pg_dump.
- Кожна копія проходить наявне реальне ізольоване відновлення PostgreSQL через `solvia-admin backup`. Копію, що не пройшла перевірку, не передаємо.
- Архіви шифрує restic. Підтверджений snapshot ID записується в журнал. При збої копія залишається локально, повторна спроба — через 10 хв. Сервіс не видаляє локальні чи віддалені копії.
- Кожна успішна копія зміни також потрапляє до віддаленої черги. Це архівне передавання, а не двостороннє злиття двох робочих БД.
- Чернетки, що залишаються на вимкненому/офлайн телефоні, неможливо включити в серверну копію. Їх передає наявна синхронізація після відновлення зв’язку; закриття зміни перевіряє готовність пристроїв.

## Налаштування віддаленого сховища — один раз на серверному ПК

1. На VPS створити окремого користувача `solvia-backup`, каталог `/srv/solvia-backups`, налаштувати доступ SSH-ключем. Звірити ключ SSH-сервера й записати його в root known_hosts; `StrictHostKeyChecking yes`, без автовизнання невідомих ключів. Для резервування обмежити цього користувача сховищем.
2. На локальному сервері створити `/etc/solvia/restic-password`, права **0600**. Зберегти цей пароль і SSH-ключ окремо від серверного диска: без пароля відновити зашифровану копію неможливо.
3. Скопіювати `offsite.example.json` у `/etc/solvia/offsite.json`, замінити VPS-домен і шлях, встановити права **0600**. Секрети не вказуються в UI і не входять у файл підключення клієнтів.
4. Один раз виконати `RESTIC_REPOSITORY=sftp:solvia-backup@DOMAIN:/srv/solvia-backups RESTIC_PASSWORD_FILE=/etc/solvia/restic-password restic init` від root.
5. `sudo solvia-continuity nightly` — контрольна копія та передавання. `sudo solvia-continuity remote-check` — повне читання й перевірка даних сховища. Результат видно в журналі резервування; відсутня конфігурація показується як проблема віддаленого копіювання.
6. Перевірити `systemctl list-timers solvia-nightly.timer solvia-shift-backup.timer` та зробити пробне відновлення на окремій машині.

Сховище та реквізити VPS у коді не задані. Реальне доставлення й зовнішнє відновлення потребують налаштування конкретного сервера. Помилки передавання не знищують локальну копію.

## Підключення нового ПК чи Android

Адміністратор генерує файл через наявне `/api/mobile-config` у налаштуваннях центру. Один формат `.solvia` підходить для ПК й телефона. Профіль v2 містить HTTPS endpoint та `server_id`, без логінів/паролів. Інсталятор сервера теж створює v2-профіль і зберігає налаштований профіль при оновленні того самого сервера.

Новий пристрій імпортує файл один раз. Повторний вхід та оновлення зберігають підключення. На ПК ручне введення доступне лише технічній Server Console; телефон підключається файлом. Уже налаштовані старі пристрої не скидаються. Локальний CA слід установити окремо: файл не обходить довіру TLS.

**Для майбутнього VPS використовуйте стабільне HTTPS/DNS-ім’я від самого початку.** Зміна DNS після міграції не потребує повторного імпорту. Уже збережена буквальна LAN IP-адреса сама на VPS-домен не перетвориться: таким пристроям потрібен одноразовий новий файл. Адреси з різними origin мають окремі сесії й чернетки; незавершені записи потрібно передати до переходу.

## Контрольований перехід на VPS

1. Пробно відновити свіжу копію в окрему БД VPS; не відкривати її працівникам. Зіставити версію застосунку, кількість записів, історію консультацій і документи. При переносі разом з БД окремо перенести пакети оновлень/необхідні файли сервера.
2. На обох кінцях установити сумісну перевірену збірку. Налаштувати чинний TLS-сертифікат домену. PostgreSQL не публікувати в інтернет.
3. Дочекатися передавання всіх телефонних чернеток. У Server Console увімкнути обслуговування — **сервер відхиляє записи з HTTP 503**, клієнти показують повідомлення й орієнтовний час, відкриті форми залишаються на місці.
4. Зробити фінальну перевірену копію, передати, відновити на VPS. `installation_identity` зберігається в БД, тому націлений профіль впізнає сервер. До відновлення зупинити фонові джоби цільового сервера.
5. Виконати `solvia-continuity preflight --url https://DOMAIN --server-id EXPECTED_64_HEX_ID`. Команда перевіряє TLS, відсутність перенаправлення та ідентичність відновленого сервера; **не підтверджує сама повноту даних** і не змінює DNS.
6. Зупинити/відгородити від запису старий сервер, переключити DNS/маршрут. Перевірити ПК, Android, прийом, збереження консультації, друк та резервування. Лише тоді зняти обслуговування на VPS. Не дозволяти одночасний запис у дві копії БД.
7. Стару БД залишити вимкненою для повернення. Після появи нових записів на VPS просте повернення DNS втратить ці зміни: потрібна окрема узгоджена процедура перенесення даних назад.

## Оновлення і збої

Server Console → «Обслуговування та повідомлення пристроям» задає повідомлення та орієнтовну тривалість. Linux updater оголошує обслуговування до зупинки API і знімає його тільки після успішної перевірки здоров’я. При помилці режим залишається для перевірки адміністратором. Час не є фальшивим прогресом; після ETA клієнти кажуть, що оновлення триває довше.

ПК опитує публічний організаційний стан; Android перевіряє його кожні 15 с, коли застосунок відкритий. Офлайн-пристрій не може миттєво отримати повідомлення; після підключення побачить актуальний стан. Телефон зберігає наявну фонову синхронізацію.

ПК й Android повідомляють «Потрібно оновити SOLVIA», показують анімацію завантаження й перевіряють пакети. Android залишає системне підтвердження встановлення та перевіряє підпис APK. Застосунок не примушує перезапуск із відкритою консультацією. Відмова/відкладення оновлення не видаляє записів.

## Поточна перевірка

Перевірено production React build, браузерні сценарії чотирьох ролей, показ/згортання обслуговування, збереження робочого екрана, існуючі JavaScript перевірки, GCC C++ сервер, Python-перевірки черги/повторів/контрольної суми та політики HTTPS. Сценарії віддаленого передавання моделюють збій та підтвердження snapshot; вони не є підтвердженням доставлення на конкретний VPS. Нові таблиці й режим запису перевіряються на реальній ізольованій PostgreSQL. Нативна збірка й інструментальні Android-перевірки запускаються в GitHub Actions; фізичне приймання пристроїв потрібне після налаштування сервера.
