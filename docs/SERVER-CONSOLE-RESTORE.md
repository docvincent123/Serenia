# Lemvori Care / SOLVIA Server Console — відновлення бази з файлу

## Для кого

Лише адміністратор **локального Linux-сервера** й окремої Server Console.
Працівники центру, психологи та реєстратура не мають кнопок керування
PostgreSQL. Ця операція **не доступна через загальний HTTP API** і не
дозволяє дистанційно виконувати довільні команди.

## Створити резервну копію

1. На серверному ПК відкрийте **SOLVIA Server Console**.
2. У вкладці **Резервні копії** натисніть **Створити резервну копію БД**.
3. Підтвердьте запит polkit адміністратора ОС.
4. Сервер зробить `pg_dump -Fc`, потім реальне пробне відновлення на
   окремій PostgreSQL-базі; лише після успішної перевірки файл набуде
   розширення `.dump` і зберігатиметься в `/var/backups/solvia`.
5. Збережіть архів і ключі від restic/SSL окремо, перевірте індикатор у
   кабінеті. Компанійний реєстр отримує тільки технічний статус.

## Відновити з файлу

**Спочатку переконайтеся, що всі психологи завершили записи та
синхронізували офлайн-чернетки.**

1. Відкрийте **SOLVIA Server Console** саме на тому комп'ютері, БД
   якого буде замінена. У вкладці **Резервні копії** оберіть
   **Відновити з файлу .dump**.
2. Системний вибір файлів дозволяє вибрати звичайний файл `.dump`.
   На екрані підтвердження чітко вказується, що дані поточної БД будуть
   повністю замінені. Введіть `ВІДНОВИТИ` та підтвердьте права ОС.
3. `solvia-admin restore-ui` копіює архів у приватний root-каталог,
   перевіряє його пробним відновленням, зупиняє джерела запису,
   створює **обов'язковий свіжий захисний backup** поточної БД,
   застосовує перевірений архів в **одній транзакції** PostgreSQL,
   оновлює схему через `--init` і перевіряє HTTPS.
4. У разі помилки міграції сервер може залишитися зупиненим для
   діагностики. Захисна копія залишається в `/var/backups/solvia`.
   **Не повторюйте відновлення навмання**, перш ніж з'ясувати причину.
5. Після успіху увійдіть знову, звірте кількість пацієнтів,
   консультацій, виписок, доступи, Android-синхронізацію, облікові
   записи, ліцензію, HTTPS та щоденне резервування.

## Перенесення на інший сервер / центр

Архів включає `installation_identity`, номер центру, ліцензії,
сеанси та приватні дані — це відновлення тієї самої інсталяції на
новому комп'ютері, **а не злиття** двох центрів. Нові записи на двох
незалежних копіях однієї БД не можна безпечно поєднати. Перед cutover
вимкніть старий сервер, переведіть DNS/HTTPS, перевірте `server_id` та
ліцензію, повторно під'єднайте клієнтів якщо змінилося ім'я сервера.

Для окремих центрів використовуйте **окремі** PostgreSQL-кластери,
ліцензії та restic/SFTP-репозиторії. Компанійний `operator-hub`
реєструє центр і показує лише його технічний стан, без автоматичного
завантаження психологічних нотаток.

## Інструкція термінала на випадок проблем із GUI

```bash
sudo solvia-admin backup
sudo solvia-admin backups
sudo solvia-admin verify-backup /path/to/center.dump
sudo solvia-admin restore /path/to/center.dump
```

Остання команда також просить ввести `ВІДНОВИТИ` у терміналі.
Реальну міграцію з даними центру проводьте тільки після тесту на
копії БД та погодженої процедури захисту медичних даних.

## Стан розробки

Реалізація знаходиться у draft PR #38. Сама наявність кнопок у коді
не означає перевірене відновлення на робочому сервері. Перед
розгортанням мають пройти Linux/Windows/Android CI, smoke-тести
PostgreSQL і **реальне відновлення тестової БД з локального архіву**
під Linux/GTK + polkit.
