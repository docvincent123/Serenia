# LemvoriLab Company Control — реєстрація центрів та віддалений стан

**Мета.** Один компанійний кабінет для реєстрації інсталяцій Lemvori Care,
перевірки їхнього стану та віддаленого контролю доставки **зашифрованих** копій.
Це **окремий сервер** від робочої БД психологічного центру.

## Архітектура

```
LemvoriLab VPS (HTTPS)
 ├─ Company Control / operator-hub (127.0.0.1:8769 за HTTPS proxy)
 │   └─ SQLite: назва центру, UUID, server_id, версія, heartbeat, стан копій
 └─ SFTP/Restic з окремим репозиторієм і ключами для КОЖНОГО центру
       ├─ center/<UUID-1> (тільки зашифровані архіви)
       └─ center/<UUID-2> (тільки зашифровані архіви)

Центр A: свій Linux, PostgreSQL, staff login, Android → outbound HTTPS heartbeat
                                          └─ restic → SFTP архів центру A
Центр B: інший Linux, інша PostgreSQL, інші облікові записи → те саме
```

Головна програма **не переключає** працівника між БД за допомогою введеного
логіна: спочатку один раз імпортується перевірений центр-профіль `.solvia`
(HTTPS URL + server_id), далі працівник входить **логіном і паролем свого закладу**.
У компанії є окремий обліковий запис оператора. Ні ліцензійний приватний ключ,
ні медичні дані не зберігаються в Company Control.

## Що реалізовано

- Компанійний логін із PBKDF2-SHA256, захищеною cookie-сесією, CSRF та
  перевіркою Origin; окремий аудит змін.
- Реєстрація центру за його постійним 64-символьним `server_id`; запобігання
  повторній реєстрації сервера.
- Одноразовий ключ агента, його ротація, окремий статус `active / paused`
  у **компанійному реєстрі** (це НЕ вимкнення роботи медичного центру).
- Індивідуальна картка стану: версія, контакт за 15 хв, статус
  віддаленого шифрованого архіву та дата підтвердженої копії.
- Linux-агент надсилає лише дозволені метадані до Company Control.
  Ідентифікатор центру перевіряється локально перед кожним запитом.
- У самому медичному сервері вже існують Ed25519 ліцензії з прив'язкою
  до `server_id`, а також `solvia-nightly.timer` і шифрування restic.

**Не реалізовано і не слід вважати увімкненим:** автоматична реєстрація через
зовнішній білінг, дистанційний SSH-доступ до клієнтських ПК, управління
клінічними записами з компанійної панелі, багатокористувацькі акаунти
замовників у Company Control, юридично значимі електронні підписи,
автоматичне об'єднання двох незалежних робочих БД.

## Запуск компанійного кабінету

Потрібен **окремий VPS або захищений сервер компанії**, Python 3.12,
HTTPS reverse proxy (наприклад, Nginx), окремий непривілейований ОС-користувач,
каталог `/var/lib/lemvori-hub` із правами 0700.

1. Встановити `operator-hub/` як `/opt/lemvori-operator/`.
   Конфігурація: `HUB_PUBLIC_ORIGIN=https://YOUR-HUB-DOMAIN`,
   `HUB_DB_PATH=/var/lib/lemvori-hub/registry.sqlite3`,
   `HUB_PORT=8769`.
2. **Один раз** від імені сервісного користувача запустити
   `python3 /opt/lemvori-operator/server.py --init-only` з тимчасовими
   `HUB_ADMIN_USER` та `HUB_ADMIN_PASSWORD` (мінімум 16 символів).
   Секрет не записувати в Git, скрипти запуску або shell history.
3. Прибрати `HUB_ADMIN_PASSWORD` з оточення перед штатним запуском.
   `python3 /opt/lemvori-operator/server.py` слухає **лише
   127.0.0.1:8769**, HTTP за межі сервера не публікувати.
4. Налаштувати HTTPS reverse proxy на вказаний точний origin із
   чинним TLS сертифікатом. Доступ до панелі обмежити VPN або allowlist IP,
   увімкнути захист входу на reverse proxy, резервувати SQLite реєстр.
5. Перевірити тести `python3 -m unittest discover -s operator-hub/tests -v`
   і ручний вхід. Ніякі паролі центрів не потрібно передавати в цю БД.

**Company Control окремий від робочої МІС.** Не розміщувати його на
медичному сервері закладу й не відкривати порт 8769 напряму в інтернет.

## Додавання нового закладу

1. Створити **окрему інсталяцію сервера й БД** через штатний інсталятор.
   Відкрити Server Console, зчитати `server_id` з параметрів ліцензії
   або `/api/health`; налаштувати назву закладу та TLS/DNS.
2. У Company Control → «Новий центр» ввести назву, місто і `server_id`.
   Зберегти **одноразовий** heartbeat-token, не передавати його працівникам.
3. На Linux-сервері центру створити конфігурацію
   `/etc/solvia/operator-hub.json` за `installer/linux/operator-hub.example.json`;
   права файлу **0600**, власник root. Сам токен у
   `/etc/solvia/operator-heartbeat-token` із правами **0600**, власник root.
4. Активувати **окремо за дозволом закладу**
   `sudo systemctl enable --now lemvori-heartbeat.timer`.
   Агент кожні 5 хв надсилає лише server_id, версію, статус і дату
   зашифрованого архіву. При помилці ніякі записи пацієнтів не губляться.
5. У Company Control відображається «На зв'язку» після першого підтвердження.
   Для працівників сформувати `.solvia` підписаний профіль підключення
   й створити їхні персональні логіни штатним адміністратором закладу.
6. Підписану ліцензію видати через **існуючу** утиліту
   `tools/issue-center-license.py`; ключ Ed25519 залишається на захищеній
   машині видавця. Віддалений heartbeat сам по собі не активує ліцензію.

## Щоденні зашифровані копії на VPS

Існуючий `solvia-nightly.timer` формує копію о 00:00 за `Europe/Kyiv`.
`solvia-continuity` перевіряє дамп і передає його через restic/SFTP,
але **лише після явної конфігурації**. Для кожного центру створіть
окремого SFTP-користувача/каталог, **окремий** restic password,
окремий SSH ключ і політику доступу. Наприклад:

```json
{
  "repository": "sftp:center-UUID@YOUR-VPS-DOMAIN:/srv/lemvori/centers/UUID",
  "password_file": "/etc/solvia/restic-password"
}
```

Шлях `/etc/solvia/offsite.json`, права 0600, root; файл пароля теж 0600.
На VPS ізолювати каталоги, вимкнути інтерактивний shell для SFTP-акаунтів.
Виконати `restic init`, пробну передачу, `solvia-continuity remote-check`
і тест відновлення на **окремому** PostgreSQL. Без окремо перевіреного
відновлення статус «архів відправлено» не означає, що центр гарантовано
можна відновити.

**Важливо:** психологічні записи та документи є особливо чутливими.
Перед централізованим зберіганням потрібні договір/підстави обробки,
повідомлення закладу, правила доступу та строків зберігання. Немає
непомітного автоматичного вивантаження БД на наш сервер.

## Перенесення БД між фізичним сервером і VPS

Використовуйте наявну процедуру з `docs/CONTINUITY-AND-VPS.md`:
перевірений pg_dump → restore у тестове середовище → порівняння записів →
перевірка TLS і `server_id` → припинення запису на старому сервері →
фінальний snapshot → preflight → зміна DNS → приймальні тести. Ніколи
не залишайте дві активні копії однієї БД з незалежними записами.
Між **різними** центрами БД автоматично не об'єднуються.
